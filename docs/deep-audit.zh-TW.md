## 確認並修正的問題

### 1. JSON 歧義與無損匯入

Go 標準 `encoding/json` 的相容行為包含後值覆蓋重複欄位、大小寫匹配及無效 Unicode
替換；僅成功反序列化不足以證明醫療原文沒有被改寫。依
[Go 官方說明](https://pkg.go.dev/encoding/json)，新增共用的前置嚴格驗證，
拒絕重複／跳脫後同名欄位、無效 UTF-8、孤立 UTF-16 代理碼、過深結構與尾隨文件。
Go 結構型別邊界另拒絕 case-fold 別名；來源資料映射維持原本大小寫區分。

可攜檢驗 JSON 另外要求精確欄名與字串型別，不能以 `result`／`Result` 互相覆蓋，
也不能將 `null` 默默當作空字串。有效中文、真正的 U+FFFD、非 BMP 字元的成對代理碼
及字面反斜線內容仍保留。錯誤只描述類型，不包含來源欄位或醫療片段。

證據：[共用驗證器](https://github.com/bestkakkoii/healthbank/blob/v1.0.3-rc.9/internal/strictjson/validate.go)、
[嚴格解析測試](https://github.com/bestkakkoii/healthbank/blob/v1.0.3-rc.9/internal/strictjson/validate_test.go)、
[可攜格式測試](https://github.com/bestkakkoii/healthbank/blob/v1.0.3-rc.9/internal/lab/structured_import_test.go)。前端資料包與個人品項同樣
使用嚴格 Unicode／重複欄位檢查，檔案讀取使用拒絕損壞輸入的 UTF-8 解碼。

### 2. 跨分頁與操作失敗的資料隔離

| 已重現情境 | 修正後行為 |
| --- | --- |
| 兩分頁先後匯入不同資料包，但模式同為 `import`；檢驗來自 B，清單仍來自 A | 每份即時檢驗回應附精確 `session_token`；安裝資料及後續設定／目錄前核對相同工作階段，不能只比較模式 |
| 另一分頁換人後，舊頁面使用共用的新 Cookie 讀取來源 | 有狀態讀取帶本頁 `X-CSRF-Token`；不相符在處理前回傳 `409 session_changed`，舊醫療內容清除 |
| 舊 Cookie／識別的請求在工作階段輪替後才抵達，晚到回應另設匿名 Cookie | 已知舊識別不再建立或發出替代 Cookie；沒有自訂標頭的原生附件請求也在缺少有效連線時直接拒絕，不覆寫目前有效連線。明確重新確認使用 `/api/session` |
| 登入／登出／匯入已在伺服器執行，但瀏覽器遺失回應 | 只重新確認工作階段；已換人或無法確認時清除舊內容，確認未變才保留。不重播操作，不虛報成功 |
| 驗證碼刷新看到另一分頁的新連線，只更新 API 全域權杖 | 由 App 統一核對身分與清除狀態，不讓權杖與畫面分屬不同連線 |
| 取消後仍有檢驗、目錄或身分確認回應抵達 | 所有階段都檢查同一操作生命週期，不再安裝已取消的結果 |
| 明確登入失效、CSRF／連線失配、輪替失敗仍留下舊資料 | 全站失效處理清除檢驗、醫療清單與臨時個人內容；普通設定修訂衝突仍可保留資料 |

伺服器的 30 分鐘閒置期限與原本固定 Cookie Max-Age 不一致，會讓持續使用者被提前切斷。
改為工作階段 Cookie，由伺服器執行滾動閒置期限，普通回應不重發舊 Cookie。
瀏覽器可能還原工作階段 Cookie，因此關閉瀏覽器不是可靠的登出承諾。

證據：[工作階段綁定](https://github.com/bestkakkoii/healthbank/blob/v1.0.3-rc.9/internal/server/session_binding_test.go)、
[生命週期](https://github.com/bestkakkoii/healthbank/blob/v1.0.3-rc.9/internal/server/session_lifetime_test.go)、
[前端 API 綁定](https://github.com/bestkakkoii/healthbank/blob/v1.0.3-rc.9/web/tests/api-session-binding.test.mjs)，另以實際 App 注入延遲、
回應遺失、身分確認失敗與跨分頁切換。所有資料與識別均為明示合成內容。

### 3. 日期、來源欄位、下載及完整性

| 問題 | 修正與界限 |
| --- | --- |
| 原始民國／西元／非標準日期在正規化後匯出時丟失 | `raw_check_date`／`raw_visit_date` 與正規化日期並存；明細、CSV、可攜 JSON/XML 保留原文及明確空值 |
| `complete` 只檢查存在非負總數，未要求與回傳筆數相等 | 只有相同期間總數等於實際長度才確認一致；不一致保留全部回傳資料及來源總數，明示尚未核對完整性 |
| 篩檢／COVID 投影遺漏有來源證據的結果、類型與日期 | 保留 Lung-RADS、乳房／HPV 來源代碼、`assay_RESULT`、檢驗模式／疾病及收件日期；不新增推斷或診斷 |
| 運動明細未確實處理失敗或識別不符，時間欄位不完整 | 驗證 `ResultStatus`、非空明細及提供時的 `ROW_ID`；分別保留日期、時、分、期間、類型及強度 |
| 空／未知明細因繼承父項目日期／院所而看似成功 | 先確認已辨識的明細原文，再繼承父項目；不能用父資料補造明細 |
| 官方檔案的 `did` 下載選擇被丟棄 | 綁定來源選擇，使用觀察到的 `app_download?gid`／`app_imgF_download?gid`；沒有該欄位才沿用原序號路徑 |
| 二進位下載收到 HTTP 200 JSON 登入逾時，未傳遞失效 | 有界讀取錯誤本文、清除連接器識別並回報 `SESSION_EXPIRED`，不交付偽裝文件 |
| 住院 PDF 清理回應明示失效卻仍當成下載成功 | 清理恰嘗試一次；緩衝 PDF 交付前傳遞已知失效；一般清理失敗仍保留未確認警告或原下載錯誤 |
| 分別合法的來源根陣列合併後超出輸出／可攜界限 | 最終投影的筆數、欄位及文字長度在替換識別前驗證；超限原子拒絕，不截斷後宣稱完整 |

另外將無效日期驗證移到任何官方權杖刷新之前。來源錯誤欄位的大小寫變體不能隱藏
登入失效，矛盾別名會拒絕。以上可重跑案例集中於
[來源完整性回歸](https://github.com/bestkakkoii/healthbank/blob/v1.0.3-rc.9/internal/nhi/audit_integrity_test.go)。公開來源路徑、欄位與新增
下載元件 SHA-256 見[資料來源契約](provider-data.md)及[文件契約](provider-documents.md)。

文件驗證涵蓋來源限制、位元組特徵、傳輸長度、容量與中斷；沒有把它宣稱為完整
PDF／ZIP 內部結構或加密內容驗證。官方正常結束傳輸的損壞原檔仍可能無法辨識。
上游暫存清理沒有已知正向確認契約，HTTP 200 也不等於已證明刪除。

### 4. 設定保存、快照與裝置端清除

CLI 曾先驗證解碼後設定，再把原始 JSON 寫入 SQL；歧義欄位可能留下未受相同白名單
約束的內容。現在持久化實際通過型別與規則檢查的標準化設定。來源發現的新項目也在
SQL 寫入前核對名稱、單位、筆數及文件容量；不符合時仍保留全部檢驗並明示未同步。

快照輸出與輸入統一 64 MiB 上限，輸出完成需成功 Sync／Close 才回報成功；
修訂值限 JavaScript 可精確表示的正整數，時間戳符合兩種資料庫共同的欄位容量。
多段 multipart 的無檔名部分不能被忽略後再接受另一檔案。所有拒絕均保留原有效狀態。

個人品項的非同步檔案讀取加入操作世代；使用者清除、取消保存同意、換內容或登出後，
晚到回呼不能恢復已清除資料／同意。單一來源匯出與完整資料包共用安全投影，
48 位即時明細／附件識別改成檔案內 `archive_N`，不保留來源操作或私有選擇欄位。
React 捕捉、未捕捉及恢復錯誤只輸出固定安全碼，不記錄原始例外與元件堆疊。

證據：server 的 `json_boundary`、`discovery_limits`、`import_limits` 測試，
store 的 `transfer_limits` 與 CLI 測試，以及前端 personal-records／health-dataset 回歸。

### 5. 精確數值、公式與研究重核

前端以 `Number()` 預先比較個人區間，會將
`[1.00000000000000000001, 1.00000000000000000002)` 誤判為空。
移除近似排序／重疊判斷，保留數字輸入檢查與原字串，交由現有後端有理數規則驗證。
新增有效極窄、相鄰半開、真正反向及次浮點精度重疊四類案例；沒有放寬後端規則。

重新核對九項成大具名參考表、NIDDK CKD-EPI 2021、KDIGO、已啟用臺北榮總門檻、
TG／低血糖來源與 Sampson 原始研究。公式係數另以原始實驗室文件交叉核對。
新增八組由 70 位精度十進位計算所得的 CKD-EPI 參考數值，涵蓋兩種公式性別變數、
多個年齡與肌酸酐分段；目錄測試核對別名不衝突、來源／規則可解析、區間合法且不重疊。

TG ≥400 不套用 Friedewald、TG >800 不外推 Sampson、Type III 排除、同次採檢與
單位／方法條件、原院直接量測值及獨立提醒均保留。研究重核沒有新增治療建議、
擴大公式適用範圍或把來源欄位自動變成臨床計算輸入。
具體原始來源與限制見[臨床參考](clinical-reference.zh-TW.md)與[比較契約](comparison-engine.md)。

### 6. 發行來源與供應鏈

原封裝可接受未提交／未追蹤來源、自訂錯誤 COMMIT 或時間戳，來源清單也可能默默忽略
symlink 目錄、在特殊檔案阻塞，或為不完整／舊版本壓縮包產生校驗碼。
新增正式封裝預檢：實際 Git 根目錄、HEAD／時間戳一致、工作樹與索引乾淨、所有
白名單輸入均受追蹤，並逐一核對與提交來源的內容／檔案集合，不只信任 `git status`。
symlink 及非一般檔案拒絕；需要的授權與文件必須存在。

校驗與上傳清單必須正好包含選定版本的 amd64、arm64、來源三個壓縮包及校驗檔。
發布時解析現有輕量／附註標籤，必須指向實際編譯提交；GitHub 查詢故障不能視為
標籤／Release 不存在。既有 Release 不替換，推標籤仍只準備草稿，授權的 main RC
更新才經完整 gates 正式公開。發布檔案的 VERSION／BUILDINFO 與校驗碼亦需一致。

Staticcheck 2026.2.2／v0.8.2 及官方不可變提交加入工具鎖定與 CI，全規則分析
`cmd/...`、`internal/...`。這些是所有第一方 Go 套件；npm 安裝目錄內第三方範例 Go
檔不是應用來源。已修正未用程式、冗餘轉換與套件／宣告註解等診斷，未停用任何規則。
第三方授權通知及 MySQL AUTHORS 重新對齊實際鎖定的來源提交。

## 明確界限

這是可獨立完成的軟體稽核與交付驗收，沒有宣稱形式化證明所有路徑永遠無缺陷。
未使用真人帳號、個人報告或正式資料庫，也未操作使用者 VPS。
真實官方登入、帳號可回傳年度／類別、原始檔產製、實體 iPhone／Safari／密碼管理員、
正式代理／CDN／作業系統保存行為依[實機驗收清單](acceptance.zh-TW.md)處理。

公開官方 JavaScript 是可觀察契約，並非官方承諾支援的 API。漏洞掃描只反映當時
可取得的公告資料；開發版 Go 標準庫缺少可比較正式語義版號的限制保留。沒有用
合成通過結果推定真實帳號完整性、個人公式適用性或任何基礎設施絕對零留存。
